# Get iT — guide de travail

Plateforme de développement personnel tout-en-un, organisée autour de quatre piliers : Physique, Mental, Social, Financier. Le document fondateur [docs/PRODUCT.md](docs/PRODUCT.md) fait foi pour la vision, le périmètre du MVP (§70) et l'ordre de construction (§89) : le relire avant toute nouvelle fonctionnalité.

## Façon de travailler

- Lire le code concerné avant de le modifier ; ne pas réécrire ce qui fonctionne par simple préférence.
- Classer chaque fonctionnalité en NOW / NEXT / LATER et garder le MVP minimal.
- Après une analyse, attendre la validation avant une refonte majeure ; expliquer avant d'ajouter une dépendance majeure.
- Signaler la dette technique et les risques produit plutôt qu'exécuter aveuglément.
- Communiquer en français. Code et identifiants en anglais, commentaires en français.

## Stack

- **Next.js 16.4** (App Router, Turbopack, Cache Components et Partial Prefetching activés). Les API diffèrent des versions précédentes : consulter `node_modules/next/dist/docs/` avant d'écrire du code Next.
- **TypeScript** strict, avec `noUncheckedIndexedAccess`.
- **Tailwind CSS v4** et **shadcn/ui** (Radix, style « nova »). Les primitives sont dans `src/components/ui` et s'ajoutent avec `npx shadcn@latest add <composant>`.
- **next-intl 4** (fr, en), avec la langue lue via `next/root-params`.
- **Prisma 7.10** : la config est dans `prisma7.config.ts` (nom imposé par cette version), le client est généré dans `src/generated/prisma`. La base est PostgreSQL sur Supabase.
- **Zod 4** pour la validation, **Vitest 5** pour les tests.


## Architecture

| Dossier                        | Rôle                                                                                        |
| ------------------------------ | ------------------------------------------------------------------------------------------- |
| `src/app/[locale]/(marketing)` | Site public                                                                                 |
| `src/app/[locale]/(app)`       | Application, réservée aux utilisateurs connectés (voir `src/features/auth/access.ts`)       |
| `src/app/[locale]/(auth)`      | Connexion, inscription, mot de passe oublié (écran divisé)                                  |
| `src/components/ui`            | Primitives shadcn                                                                           |
| `src/components`               | Composants partagés (layout, brand, empty-state, locale-switcher)                           |
| `src/features/<domaine>`       | Composants et schémas Zod d'un domaine                                                      |
| `src/server/<domaine>`         | Logique métier et autorisation (`server-only`), appelée par les Server Actions et `/api/v1` |
| `src/i18n`                     | Routage, configuration de requête et navigation localisée                                   |
| `src/config`                   | Constantes produit (piliers, site)                                                          |
| `messages/`                    | Textes de l'interface (`fr.json` est la langue source)                                      |

La logique métier ne vit jamais dans les composants : le web et la future app mobile (Expo) appelleront les mêmes services de `src/server`.

## Règles

- **Textes** : aucun texte en dur dans les composants. Chaque clé existe dans `messages/fr.json` **et** `messages/en.json` (un test vérifie la parité). Les arguments numériques s'écrivent `{n, number}`, les pluriels `{n, plural, …}`. En français, utiliser l'apostrophe typographique ’ et une espace insécable avant « : ».
- **Liens internes** : utiliser `Link`, `redirect` et `useRouter` de `@/i18n/navigation`, pas ceux de `next/link`, pour conserver la langue.
- **Composants** : Server Components par défaut ; `"use client"` uniquement pour l'interactivité. Les `id` de formulaire passent par `useId()` : Next garde la page précédente cachée dans le DOM, des `id` fixes y seraient dupliqués. Un Server Component ne passe à un Client Component que des valeurs sérialisables (jamais une icône ou une fonction ; seules les Server Actions font exception).
- **Cache Components** : pas de `new Date()`, `Date.now()` ni `Math.random()` dans un Server Component sans `io()` (de `next/cache`) ou `"use cache"`. Les données propres à l'utilisateur vont dans un `<Suspense>`. `error.tsx` reçoit `retry()`. `usePathname`, `useSearchParams` et `params` suspendent sur les routes à paramètre dynamique (ex. `/goals/[id]`) : les isoler dans un `<Suspense>` (voir la barre latérale), ou lire l'adresse au moment de l'action.
- **Sécurité** : valider toute entrée côté serveur avec Zod, vérifier l'autorisation sur chaque ressource et ne jamais faire confiance au client. Les données passent uniquement par `src/server/db.ts`, jamais du navigateur vers Supabase. Activer le RLS (sans policy) sur toutes les tables pour que la clé publique Supabase n'expose rien : chaque migration qui crée une table ajoute `ALTER TABLE … ENABLE ROW LEVEL SECURITY` (un test le vérifie).
- **Authentification** : Supabase Auth sert uniquement à la session (`src/server/supabase`). Le proxy ne fait qu'une redirection rapide ; chaque service et chaque Server Action revérifie la session avec `requireUser()` (`src/server/auth/session.ts`). Une nouvelle section de l'app s'ajoute à `PROTECTED_PATHS`. `next/root-params` est indisponible dans les Server Actions : les formulaires envoient la langue dans un champ caché `locale`. **Bêta privée** : avec `SIGNUP_INVITE_CODE` (serveur seulement), l'inscription demande ce code (`src/server/auth/invite.ts`, comparé sans majuscules ni espaces autour, en temps constant) ; il est gardé dans les métadonnées du compte et revérifié à la création du profil (`openSession`), donc un compte créé directement chez Supabase n'entre pas (`inviteRequired`, la session est refermée). La page d'inscription est prérendue : changer le code demande un nouveau déploiement.
- **Mise en ligne** : Vercel (plan Pro), région de Montréal `yul1` (`vercel.json`), déploiement automatique de `main` ; étapes dans le README. Pendant la bêta, la base est partagée avec le développement : appliquer une migration (`npm run db:deploy`) puis envoyer **aussitôt** le code qui va avec, et ne jamais supprimer une colonne encore lue par la version en ligne.
- **Utilisateur courant** : les pages lisent le profil avec `getCurrentProfile()` (`src/server/profile/service.ts`), dans un `<Suspense>`. Les services reçoivent toujours l'`userId` de la session, jamais du client, et nomment les colonnes écrites (jamais `data: { ...input }` : l'entrée validée contient aussi la langue). Tant que `onboardedAt` est vide, l'utilisateur est renvoyé vers `/onboarding` ; s'il manque ses renseignements du compte (comptes créés avant), vers l'écran unique `/onboarding/details` (`DETAILS_PATH`, garde dans `DayPanel`). **Renseignements du compte** (`src/features/profile/details.ts`, fonctions pures testées ; `src/server/profile/details.ts`) : date de naissance complète (`birthDate`, **16 ans et plus**, `MIN_AGE`, vérifié dans le fuseau de la personne), sexe à la naissance (homme ou femme), pays (Canada ou États-Unis), province ou État, et région administrative au Québec (mêmes clés que le Marketplace). Demandés à l'étape « À propos de toi » de l'onboarding (l'ancienne autoévaluation sur 5 a été retirée ; `pillar_assessments` garde les anciennes réponses), modifiables dans Réglages (`DetailsSettings`), privés : jamais montrés aux autres membres. L'inscription demande aussi de retaper le mot de passe (`confirmPassword`). Toute nouvelle table liée à l'utilisateur référence `profiles` avec `onDelete: Cascade`, pour que la suppression de compte (`src/server/account/service.ts`) efface tout.
- **Base de données** : modèles en PascalCase, tables et colonnes en snake_case (`@@map`/`@map`), dates en `timestamptz`, jours du calendrier (échéance, date cible) en `@db.Date` via `src/lib/dates.ts`, formatés avec `timeZone: "UTC"`. Les champs « jour » (habitudes, séries) dépendent du fuseau de l'utilisateur (`UserSettings.timeZone`).
- **Séries** (décision du fondateur, 2026-11-01 : elles **remplacent l'XP**, retirée partout) : un **jour actif** = au moins une action ce jour-là (habitude cochée, tâche, jalon ou objectif terminé, check-in, page de journal), dans le fuseau de la personne ; lu dans les tables des actions elles-mêmes par `getActivity` (`src/server/streaks/service.ts`, aussi par pilier : le pilier de l'habitude ou de l'objectif, check-in et journal comptent pour le mental ; une tâche sans objectif n'a pas de pilier). Règles pures testées dans `src/features/streaks/rules.ts` : `dayStreak` (série du jour ; aujourd'hui pas encore actif ne la casse pas avant minuit, avec le record), `weekStreak` (série d'un objectif : semaines d'affilée où un jalon, une tâche ou une habitude liés ont été faits, `getGoalActivity`), paliers `STREAK_MILESTONES` (7, 30, 100, 365 jours) fêtés dans « Ma journée » (`StreakBanner`) et partageables dans le Centre (progrès `dayStreak`, 3 jours au moins, recalculé par le serveur). « Ma journée » montre la flamme (`StreakBadge`, allumée dès la première coche, `DayPlan.streak`) et « Journée parfaite » quand tout est fait. Le niveau ne vient plus jamais des actions : il est **mesuré** (Ranked ; lot B à venir : niveaux par seuils de population et objectifs de niveau obligatoires). La table `xp_events` et l'enum `XpSource` ne sont plus lus ni écrits : à supprimer dans une migration plus tard, quand plus aucune version en ligne ne les lit.
- **Get iT AI** : tout passe par la couche d'abstraction `src/server/ai` (`types.ts`) ; le SDK d'Anthropic n'est importé que dans `claude.ts` (modèle, effort, repli `fallbacks: "default"`). La clé `ANTHROPIC_API_KEY` reste côté serveur (jamais `NEXT_PUBLIC_`, `env.ts` le refuse). Aucun appel sans l'accord de l'utilisateur (`UserSettings.aiConsentAt`, Loi 25). Chaque appel réserve d'abord une ligne `ai_requests` (limite de 20 par jour, jetons enregistrés pour suivre le coût). Les consignes sont dans `src/features/coach/prompts.ts`, le contexte envoyé est résumé et borné dans `src/features/coach/context.ts` (jamais l'historique brut). Les réponses s'affichent sans HTML injecté (`message-format.ts`). Le coach peut **proposer** des ajouts (objectif, habitude, tâche, jalon) avec les outils `propose_*` de `src/features/coach/coach-tools.ts` : chaque appel est revalidé (`parseToolCall`), enregistré dans `coach_actions` et affiché en carte ; rien n'est créé avant le clic « Ajouter », qui passe par les services habituels (`src/server/coach/actions.ts`, une seule décision par proposition). Ne jamais donner au modèle un outil qui modifie les données sans confirmation. Pour les tests de bout en bout : `AI_PROVIDER=fake` (réponses factices, refusé en production). **Plan d'un objectif en conversation** (2026-10-27) : « Proposer un plan » demande d'abord 3 à 5 questions sur la situation de la personne (`generateGoalQuestions`, consignes `goalQuestionsInstructions`, sortie bornée par `normalizeGoalQuestions`), affichées comme une conversation ; les réponses (facultatives, `goalAnswersSchema`) sont citées dans la demande de plan comme des chaînes JSON, jamais comme des consignes (`answersSection`). Questions et plan comptent chacun pour une requête (`goal_plan`). « Modifier avec Get iT AI » dans le calendrier : voir Mon développement (`item_edit`).
- **Centre Get iT** : les limites et schémas vivent dans `src/features/community/rules.ts`, la logique dans `src/server/community` (fil, publications, membres, modération). Il faut un nom d'utilisateur et les règles acceptées (`UserSettings.communityRulesAt`) avant de participer ; un compte suspendu (`Profile.suspendedUntil`) lit mais ne publie, ne commente ni ne réagit. Objectifs, habitudes et check-ins restent privés : seul un progrès choisi est partagé, figé au moment du partage (`posts.progress`), à partir d'une référence revérifiée par le serveur (jamais le texte du navigateur). Chaque lecture exclut les personnes bloquées dans les deux sens (`getBlockedIds`). Trois signalements de personnes différentes masquent un contenu en attendant la modération ; les décisions revérifient le rôle (`Profile.role`) et retrouvent l'auteur en base. L'activité sociale ne compte pas dans les séries. **Stories** (décision du fondateur, 2026-10-27 ; remplacent « Progrès du jour ») : la page de la Communauté commence par la rangée (`StoryRow`, `src/features/stories`, bulles en **carrés arrondis**, d'après la maquette « Bento ») : ma story (bouton « + » pour en ajouter) puis celles de mes **contacts seulement** (jamais des autres membres, blocages exclus), une photo ou une vidéo, visibles **24 heures** (`stories`, `expires_at`, règles pures dans `src/features/stories/rules.ts`, logique dans `src/server/stories/service.ts`). Même chaîne d'envoi vérifié que les publications (`requestUploads` puis `verifyMedia`, dossier `posts/<userId>`), 20 par 24 h. **Studio** (décision du fondateur, 2026-10-30 : « comme Instagram et Facebook », `StoryStudio`, `story-studio.tsx`) : cadre 9:16 où l'on pose des textes (5 écritures `STORY_FONTS`, 10 couleurs, taille, fond plein ou voilé, alignement), des emoji (`emoji.ts`, sans service externe) et des stickers Get iT (heure, date, lieu, @mention d'un contact, #hashtag, série d'une habitude, pilier, sondage à deux choix, question) ; chaque élément se déplace au doigt, s'agrandit et tourne à deux doigts, se jette dans la corbeille (et au clavier : flèches, + et −, [ et ], Suppr). Les éléments sont un JSON `stories.overlays` (position en part du cadre, tailles en `cqw`), validé par `storyOverlaysSchema` (`src/features/stories/studio.ts` : 20 au plus, 5 mentions, un seul sondage ou une seule question) et relu élément par élément (`readOverlays`) ; le serveur fige la mention (contact non bloqué avec un nom d'utilisateur) et la série (calculée par `computeStreaks`) au moment de publier (`resolveOverlays`). Le même rendu sert au studio et à la visionneuse (`story-overlays.tsx`, `StoryFrame`). **Musique** : catalogue Get iT **libre de droits** (`music_tracks`, fichiers `music/<uuid>` du compartiment privé, liens temporaires), ajouté par l'équipe (rôle `admin`) dans Réglages › Musique des stories (`/settings/music`, introuvable pour les autres ; fichier envoyé directement au stockage puis revérifié, licence obligatoire) ; onglets Tendances (les plus utilisés ces 7 jours), Pour toi (`rankForYou` : piliers prioritaires, morceaux des contacts, déjà choisis) et Recherche (titre, artiste, ambiance) ; un extrait de 15 s (`MUSIC_CLIP_MS`, `clampClipStart`) joue sur la story (une photo avec musique dure 15 s, une vidéo avec musique est muette et l'extrait boucle) ; retirer un morceau le cache du studio sans toucher aux stories publiées. Les vraies chansons tendance demanderont un fournisseur sous licence (NEXT : Feed.fm, Epidemic Sound ; jamais les extraits Spotify ou Apple). Visionneuse plein écran toujours sombre (5 s par photo, 15 s avec une musique, la vidéo jusqu'au bout, toucher à gauche ou à droite, appui long = pause, **glisser vers le bas ferme la story** et ramène à la Communauté comme sur Instagram et Facebook, **glisser sur le côté** passe à la personne suivante (vers la gauche) ou revient à la précédente (vers la droite), et elle arrive en glissant (`story-in-right`, `story-in-left`), son coupé ou non gardé d'une story à l'autre) ; l'anneau « déjà vu » reste gardé dans le navigateur (`src/features/stories/seen-store.ts`), mais **l'auteur voit qui a vu sa story** (décision du fondateur, 2026-10-30 : `story_views`, « Vu par » sous sa story, avec les votes du sondage — qui a choisi quoi — et les réponses à la question ; personnes bloquées exclues). On vote une fois (`story_poll_votes`), on répond une fois à la question (`story_answers`, 200 caractères, lue par l'auteur seulement, notification `story`). La barre « Répondre à… » et les réactions rapides (`STORY_REACTIONS`) envoient un message `kind: "story"` à l'auteur (voir Messagerie). Signalement (`content_reports.story_id`, masquée à 3 signalements, retirée ou rétablie par la modération) ; l'auteur la supprime. Les stories terminées et leurs fichiers sont effacés par `purgeExpiredStories` après le rendu de la Communauté (`after()`), une story signalée et non traitée 7 jours de plus. Les progrès partagés restent des publications du fil. Les photos vont d'un bord à l'autre sur téléphone ; « J'aime » et les commentaires sont sous le média, au même endroit pour une photo et une vidéo (décision du fondateur, 2026-10-30), et un double-tap aime une photo ; `useBravo` (`reaction-store.ts`) garde le même « J'aime » dans le fil et sur les pages des publications. **Enregistrer** (icône sous chaque publication, `setPostSaved` dans `src/server/community/saves.ts`) : toute publication lisible, 500 au plus (`MAX_SAVED_POSTS`), privé (jamais montré à l'auteur), effacé avec le compte ou la publication (`post_saves`) ; un compte suspendu peut encore enregistrer. **Partager** (`ShareDialog`) : dans mon fil (`sharePost` : la publication d'un autre membre, citée sous mon mot par `posts.shared_post_id` ; partager un partage renvoie à l'origine, une seule fois par publication, le partage disparaît avec l'origine et compte dans la limite de publications), à une discussion ou un contact (message `kind: "post"`, voir Messagerie), « Copier le lien » et « Autres applis » (partage du téléphone). Le lien `/community/posts/[id]` est réservé aux membres connectés (`getFeedPost`, mêmes règles de visibilité et de blocage que le fil). Une publication citée (partage ou message) est relue pour la personne qui lit (`sharedPostsFor`) : masquée, retirée ou d'une personne bloquée, elle devient « n'est plus disponible ».
- **Photos et vidéos** : limites et schémas dans `src/features/community/media.ts` (4 photos ou 1 vidéo de 60 s / 50 Mo), stockage dans le compartiment **privé** « media » de Supabase Storage, utilisé uniquement par `src/server/storage/service.ts` (clé `SUPABASE_SECRET_KEY`, serveur seulement, facultative : sans elle, les boutons photo/vidéo sont masqués). **Seule exception** à « rien du navigateur vers Supabase » (approuvée par le fondateur) : le navigateur envoie un fichier directement au stockage avec une autorisation à usage unique créée par le serveur pour ce chemin (`requestUploads`) ; le serveur revérifie ensuite le fichier (présence, taille, type) avant de le joindre (`verifyMedia`). La lecture passe par des liens temporaires d'une heure. **Caméra** (2026-10-30) : « Prendre une photo » ouvre directement la caméra du téléphone (`capture`), « Filmer une vidéo » laisse le téléphone proposer le caméscope (avec `capture`, iPhone et Samsung s'ouvraient en mode photo) ; dans le formulaire de publication, à l'ouverture du studio des stories et dans la Messagerie (`CameraMenu`, `CameraInputs` de `camera-menu.tsx`). Les photos sont réduites et réencodées dans le navigateur (`media-client.ts`), ce qui retire la position GPS ; les vidéos ne sont pas encore réencodées (NEXT : Mux ou Cloudflare Stream). Supprimer une publication ou un compte supprime aussi ses fichiers. **Vues des vidéos** (2026-10-28) : une vue par personne et par publication après 2 secondes regardées (`recordVideoView`, `post_video_views`), jamais celle de l'auteur ; le nombre est public (pastille en haut à gauche de la vidéo, `FeedPost.videoViews`), qui a regardé ne l'est pas. Next garde les pages quittées cachées dans le DOM (Activity) : tout média qui joue (vidéo, audio) se met en pause dans le nettoyage d'un `useLayoutEffect`, sinon le son continue dans une autre catégorie (voir `PostVideo` : pause aussi hors de l'écran, une seule vidéo à la fois).
- **Messagerie** : règles et limites dans `src/features/messages/rules.ts` (fonctions pures testées : `sendPermission`, `layoutMessages`), logique dans `src/server/messages/service.ts`. Conversations privées entre membres du Centre, une seule par paire (`directKey`). Le premier message d'une personne inconnue arrive comme une **demande** : un seul message avant l'acceptation ; refuser la retire sans prévenir l'expéditeur. Chaque fonction revérifie la participation et les blocages (dans les deux sens). **« Vu »** (décision du fondateur, 2026-10-30) : dans une conversation à deux, « Vu » s'affiche sous mon dernier message quand l'autre personne l'a lu depuis (`ConversationState.otherReadAt`, sa `lastReadAt`, mise à jour à l'ouverture et à chaque nouveau message reçu ; rien tant qu'elle n'a pas accepté la conversation ; pas encore dans les discussions de groupe). **En ligne** (décision du fondateur, 2026-10-31, comme le rond vert d'Instagram) : un petit rond orange en bas à droite de la photo (`Avatar online`) des contacts en ligne, dans la boîte, les contacts et l'en-tête de conversation (« En ligne »), et un bouton « En ligne · N » qui filtre la boîte (contacts en ligne, leur conversation ou « Écrire »). Règles pures dans `src/features/presence/rules.ts` (`isOnline` : vu depuis 2 minutes), logique dans `src/server/presence/service.ts` : `profiles.last_seen_at` avance au plus une fois par minute avec le rafraîchissement de la pastille (`countUnreadAction`, page visible) ; visible par les **contacts seulement** (blocages exclus) et **réciproque** : le réglage « Montrer quand je suis en ligne » (`UserSettings.showPresence`, Réglages › Présence en ligne) cache la sienne et celle des autres. Les messages ne sont jamais envoyés à Get iT AI ; un message signalé n'est visible par la modération que lui seul. Pas encore de temps réel : la conversation ouverte se rafraîchit toutes les 3 secondes, la boîte toutes les 10, la pastille toutes les 30 (`UnreadPoller`). **Pactes** (défi à deux) : règles pures dans `src/features/messages/pacts.ts` (`pactProgress`, `pactNeed`, `pactOutcome`), logique dans `src/server/messages/pacts.ts`. Un seul pacte ouvert par conversation (index unique partiel) ; chacun relie une habitude dont seul le « fait / pas fait » est partagé ; le pacte commence le lendemain de l'accord ; un jour manqué ne casse que la série commune ; la fin est réglée à l'ouverture de la conversation (`settlePacts`, pas de tâche planifiée) ; quitter montre seulement « Le pacte est terminé ». Les étapes (proposition, fin, arrêt) sont des messages `kind: "pact"` affichés selon l'état du pacte. Le pacte n'ajoute rien aux séries : l'habitude y compte déjà. **En haut de la Messagerie** (2026-10-29), les pactes à deux en cours se font glisser d'une carte à l'autre (`PactCarousel`, `listActivePacts`, blocages exclus) : « Pacte en cours » et « Jour x/y » sont au-dessus des cartes, et chaque carte montre sur une ligne de 6 h à 22 h l'heure où chacun a fait sa part. **« Faire ma part »** (carrousel et bandeau de la conversation) ouvre `PartTimeDialog` : on choisit l'heure, aujourd'hui et jamais après maintenant (`completePactPart`, revérifié par le serveur), gardée en minutes dans le fuseau de la personne (`habit_completions.done_minute` ; sans choix, l'heure de la coche). **Pactes de groupe** (discussion d'un groupe privé, `src/server/messages/group-pacts.ts`, `GroupPactPanel` en haut de la discussion ; règles pures `groupPactProgress`, `groupPactOutcome`) : proposé à tous les membres actifs (sauf personnes bloquées), chacun le rejoint en reliant sa propre habitude (ou en la créant) jusqu'au premier jour ; il commence le lendemain de la première acceptation, avec ceux qui ont accepté (2 au moins) ; réussi si **80 % des participants** ont fait assez de jours ; quitter retire seulement soi-même (sous 2 participants, le pacte se termine). `proposePactAction`, `respondPactAction` et `cancelPactAction` choisissent la version à deux ou de groupe selon la conversation. **Photos et vidéo** dans les messages : mêmes limites et envois vérifiés que les publications (`message_media`, `messages.media_count`, autorisation `requestMessageUploads` seulement là où la personne peut écrire) ; un message peut n'avoir que des photos (petit bouton d'options à la place de la bulle) ; liens lus par le cache d'`avatarUrls` (la conversation se rafraîchit toutes les 3 secondes) ; supprimer le message (ou le retirer en modération) supprime ses fichiers ; la modération voit les photos du message signalé. **Publication envoyée** : message `kind: "post"` (`messages.post_id`, mis à null si la publication est supprimée), envoyé depuis « Partager » d'une publication (`sendPostAction` : discussions récentes puis contacts, `listShareTargets` ; la discussion est créée au besoin et suit les règles de demande) ; la bulle montre un aperçu et « Voir la publication » mène à son lien. **Réponse à une story** : message `kind: "story"` (`messages.story_id`, mis à null quand la story est effacée), envoyé depuis la visionneuse (`replyToStory` : la discussion est créée au besoin) ; Ils ne comptent pas dans les 3 objectifs personnels par pilier, ne se modifient, ne se terminent ni ne se suppriment à la main (le serveur refuse) ; étiquette « Objectif de niveau · niveau N » et bouton « Mettre à jour ma mesure » (`/profile/ranked?mesure=<mesure>` ouvre la fenêtre).
