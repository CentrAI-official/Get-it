# Get iT — guide de travail

Plateforme de développement personnel tout-en-un, organisée autour de quatre piliers : Physique, Mental, Social, Financier. Le document fondateur [docs/PRODUCT.md](docs/PRODUCT.md) fait foi pour la vision, le périmètre du MVP (§70) et l'ordre de construction (§89) : le relire avant toute nouvelle fonctionnalité.

## Façon de travailler

- Lire le code concerné avant de le modifier ; ne pas réécrire ce qui fonctionne par simple préférence.
- Classer chaque fonctionnalité en NOW / NEXT / LATER et garder le MVP minimal.
- Après une analyse, attendre la validation avant une refonte majeure ; expliquer avant d'ajouter une dépendance majeure.
- Signaler la dette technique et les risques produit plutôt qu'exécuter aveuglément.
- Communiquer en français. Code et identifiants en anglais, commentaires en français.

## Stack

- **Next.js 16.4** (App Router, Turbopack, Cache Components et Partial Prefetching activés). Les API diffèrent des versions précédentes : consulter `node_modules/next/dist/docs/` avant d'écrire du code Next.
- **TypeScript** strict, avec `noUncheckedIndexedAccess`.
- **Tailwind CSS v4** et **shadcn/ui** (Radix, style « nova »). Les primitives sont dans `src/components/ui` et s'ajoutent avec `npx shadcn@latest add <composant>`.
- **next-intl 4** (fr, en), avec la langue lue via `next/root-params`.
- **Prisma 7.10** : la config est dans `prisma7.config.ts` (nom imposé par cette version), le client est généré dans `src/generated/prisma`. La base est PostgreSQL sur Supabase.
- **Zod 4** pour la validation, **Vitest 5** pour les tests.

## Commandes

```bash
npm run dev          # serveur de développement
npm run dev:mobile   # idem, ouvert au réseau Wi-Fi local (tester sur un vrai téléphone)
npm run check        # lint + typecheck + tests (à lancer avant de conclure une tâche)
npm run build        # build de production (vérifie aussi le prérendu)
npm run format       # Prettier
npm run db:migrate   # nouvelle migration Prisma (nécessite DIRECT_URL)
npm run db:deploy    # applique les migrations existantes
npm run db:generate  # régénère le client Prisma (puis redémarrer npm run dev : le client est conservé entre les rechargements)
```

## Architecture

| Dossier                        | Rôle                                                                                        |
| ------------------------------ | ------------------------------------------------------------------------------------------- |
| `src/app/[locale]/(marketing)` | Site public                                                                                 |
| `src/app/[locale]/(app)`       | Application, réservée aux utilisateurs connectés (voir `src/features/auth/access.ts`)       |
| `src/app/[locale]/(auth)`      | Connexion, inscription, mot de passe oublié (écran divisé)                                  |
| `src/components/ui`            | Primitives shadcn                                                                           |
| `src/components`               | Composants partagés (layout, brand, empty-state, locale-switcher)                           |
| `src/features/<domaine>`       | Composants et schémas Zod d'un domaine                                                      |
| `src/server/<domaine>`         | Logique métier et autorisation (`server-only`), appelée par les Server Actions et `/api/v1` |
| `src/i18n`                     | Routage, configuration de requête et navigation localisée                                   |
| `src/config`                   | Constantes produit (piliers, site)                                                          |
| `messages/`                    | Textes de l'interface (`fr.json` est la langue source)                                      |

La logique métier ne vit jamais dans les composants : le web et la future app mobile (Expo) appelleront les mêmes services de `src/server`.

## Règles

- **Textes** : aucun texte en dur dans les composants. Chaque clé existe dans `messages/fr.json` **et** `messages/en.json` (un test vérifie la parité). Les arguments numériques s'écrivent `{n, number}`, les pluriels `{n, plural, …}`. En français, utiliser l'apostrophe typographique ’ et une espace insécable avant « : ».
- **Liens internes** : utiliser `Link`, `redirect` et `useRouter` de `@/i18n/navigation`, pas ceux de `next/link`, pour conserver la langue.
- **Composants** : Server Components par défaut ; `"use client"` uniquement pour l'interactivité. Les `id` de formulaire passent par `useId()` : Next garde la page précédente cachée dans le DOM, des `id` fixes y seraient dupliqués. Un Server Component ne passe à un Client Component que des valeurs sérialisables (jamais une icône ou une fonction ; seules les Server Actions font exception).
- **Cache Components** : pas de `new Date()`, `Date.now()` ni `Math.random()` dans un Server Component sans `io()` (de `next/cache`) ou `"use cache"`. Les données propres à l'utilisateur vont dans un `<Suspense>`. `error.tsx` reçoit `retry()`. `usePathname`, `useSearchParams` et `params` suspendent sur les routes à paramètre dynamique (ex. `/goals/[id]`) : les isoler dans un `<Suspense>` (voir la barre latérale), ou lire l'adresse au moment de l'action.
- **Sécurité** : valider toute entrée côté serveur avec Zod, vérifier l'autorisation sur chaque ressource et ne jamais faire confiance au client. Les données passent uniquement par `src/server/db.ts`, jamais du navigateur vers Supabase. Activer le RLS (sans policy) sur toutes les tables pour que la clé publique Supabase n'expose rien : chaque migration qui crée une table ajoute `ALTER TABLE … ENABLE ROW LEVEL SECURITY` (un test le vérifie).
- **Authentification** : Supabase Auth sert uniquement à la session (`src/server/supabase`). Le proxy ne fait qu'une redirection rapide ; chaque service et chaque Server Action revérifie la session avec `requireUser()` (`src/server/auth/session.ts`). Une nouvelle section de l'app s'ajoute à `PROTECTED_PATHS`. `next/root-params` est indisponible dans les Server Actions : les formulaires envoient la langue dans un champ caché `locale`. **Bêta privée** : avec `SIGNUP_INVITE_CODE` (serveur seulement), l'inscription demande ce code (`src/server/auth/invite.ts`, comparé sans majuscules ni espaces autour, en temps constant) ; il est gardé dans les métadonnées du compte et revérifié à la création du profil (`openSession`), donc un compte créé directement chez Supabase n'entre pas (`inviteRequired`, la session est refermée). La page d'inscription est prérendue : changer le code demande un nouveau déploiement.
- **Mise en ligne** : Vercel (plan Pro), région de Montréal `yul1` (`vercel.json`), déploiement automatique de `main` ; étapes dans le README. Pendant la bêta, la base est partagée avec le développement : appliquer une migration (`npm run db:deploy`) puis envoyer **aussitôt** le code qui va avec, et ne jamais supprimer une colonne encore lue par la version en ligne.
- **Utilisateur courant** : les pages lisent le profil avec `getCurrentProfile()` (`src/server/profile/service.ts`), dans un `<Suspense>`. Les services reçoivent toujours l'`userId` de la session, jamais du client, et nomment les colonnes écrites (jamais `data: { ...input }` : l'entrée validée contient aussi la langue). Tant que `onboardedAt` est vide, l'utilisateur est renvoyé vers `/onboarding` ; s'il manque ses renseignements du compte (comptes créés avant), vers l'écran unique `/onboarding/details` (`DETAILS_PATH`, garde dans `DayPanel`). **Renseignements du compte** (`src/features/profile/details.ts`, fonctions pures testées ; `src/server/profile/details.ts`) : date de naissance complète (`birthDate`, **16 ans et plus**, `MIN_AGE`, vérifié dans le fuseau de la personne), sexe à la naissance (homme ou femme), pays (Canada ou États-Unis), province ou État, et région administrative au Québec (mêmes clés que le Marketplace). Demandés à l'étape « À propos de toi » de l'onboarding (l'ancienne autoévaluation sur 5 a été retirée ; `pillar_assessments` garde les anciennes réponses), modifiables dans Réglages (`DetailsSettings`), privés : jamais montrés aux autres membres. L'inscription demande aussi de retaper le mot de passe (`confirmPassword`). Toute nouvelle table liée à l'utilisateur référence `profiles` avec `onDelete: Cascade`, pour que la suppression de compte (`src/server/account/service.ts`) efface tout.
- **Base de données** : modèles en PascalCase, tables et colonnes en snake_case (`@@map`/`@map`), dates en `timestamptz`, jours du calendrier (échéance, date cible) en `@db.Date` via `src/lib/dates.ts`, formatés avec `timeZone: "UTC"`. Les champs « jour » (habitudes, séries) dépendent du fuseau de l'utilisateur (`UserSettings.timeZone`).
- **XP** : le barème, la limite quotidienne de tâches et la courbe des niveaux vivent dans `src/features/xp/rules.ts` (fonctions pures testées). Toute action qui rapporte de l'XP l'écrit dans `xp_events` **dans la même transaction** que l'action (`src/server/xp/service.ts`) ; chaque ligne pointe vers son action (clé étrangère en cascade), donc annuler ou supprimer l'action retire son XP. Une nouvelle source d'XP ajoute une valeur à l'enum `XpSource`, sa colonne et la contrainte `xp_events_source_check`. La valeur d'enum s'ajoute dans une migration à part, avant celle qui l'utilise : Postgres refuse une valeur ajoutée dans la même transaction (voir `20261025120000_journal_xp_source`).
- **Get iT AI** : tout passe par la couche d'abstraction `src/server/ai` (`types.ts`) ; le SDK d'Anthropic n'est importé que dans `claude.ts` (modèle, effort, repli `fallbacks: "default"`). La clé `ANTHROPIC_API_KEY` reste côté serveur (jamais `NEXT_PUBLIC_`, `env.ts` le refuse). Aucun appel sans l'accord de l'utilisateur (`UserSettings.aiConsentAt`, Loi 25). Chaque appel réserve d'abord une ligne `ai_requests` (limite de 20 par jour, jetons enregistrés pour suivre le coût). Les consignes sont dans `src/features/coach/prompts.ts`, le contexte envoyé est résumé et borné dans `src/features/coach/context.ts` (jamais l'historique brut). Les réponses s'affichent sans HTML injecté (`message-format.ts`). Le coach peut **proposer** des ajouts (objectif, habitude, tâche, jalon) avec les outils `propose_*` de `src/features/coach/coach-tools.ts` : chaque appel est revalidé (`parseToolCall`), enregistré dans `coach_actions` et affiché en carte ; rien n'est créé avant le clic « Ajouter », qui passe par les services habituels (`src/server/coach/actions.ts`, une seule décision par proposition). Ne jamais donner au modèle un outil qui modifie les données sans confirmation. Pour les tests de bout en bout : `AI_PROVIDER=fake` (réponses factices, refusé en production). **Plan d'un objectif en conversation** (2026-10-27) : « Proposer un plan » demande d'abord 3 à 5 questions sur la situation de la personne (`generateGoalQuestions`, consignes `goalQuestionsInstructions`, sortie bornée par `normalizeGoalQuestions`), affichées comme une conversation ; les réponses (facultatives, `goalAnswersSchema`) sont citées dans la demande de plan comme des chaînes JSON, jamais comme des consignes (`answersSection`). Questions et plan comptent chacun pour une requête (`goal_plan`).
- **Centre Get iT** : les limites et schémas vivent dans `src/features/community/rules.ts`, la logique dans `src/server/community` (fil, publications, membres, modération). Il faut un nom d'utilisateur et les règles acceptées (`UserSettings.communityRulesAt`) avant de participer ; un compte suspendu (`Profile.suspendedUntil`) lit mais ne publie, ne commente ni ne réagit. Objectifs, habitudes et check-ins restent privés : seul un progrès choisi est partagé, figé au moment du partage (`posts.progress`), à partir d'une référence revérifiée par le serveur (jamais le texte du navigateur). Chaque lecture exclut les personnes bloquées dans les deux sens (`getBlockedIds`). Trois signalements de personnes différentes masquent un contenu en attendant la modération ; les décisions revérifient le rôle (`Profile.role`) et retrouvent l'auteur en base. Aucune XP pour l'activité sociale. **Stories** (décision du fondateur, 2026-10-27 ; remplacent « Progrès du jour ») : la page de la Communauté commence par la rangée (`StoryRow`, `src/features/stories`) : ma story (bouton « + » pour en ajouter) puis celles de mes **contacts seulement** (jamais des autres membres, blocages exclus), une photo ou une vidéo et une légende de 200 caractères, visibles **24 heures** (`stories`, `expires_at`, règles pures dans `src/features/stories/rules.ts`, logique dans `src/server/stories/service.ts`). Même chaîne d'envoi vérifié que les publications (`requestUploads` puis `verifyMedia`, dossier `posts/<userId>`), 20 par 24 h. Visionneuse plein écran toujours sombre (5 s par photo, la vidéo jusqu'au bout, toucher à gauche ou à droite, appui long = pause) ; « déjà vu » gardé dans le navigateur seulement (`src/features/stories/seen-store.ts`, jamais montré à l'auteur). Signalement (`content_reports.story_id`, masquée à 3 signalements, retirée ou rétablie par la modération) ; l'auteur la supprime. Les stories terminées et leurs fichiers sont effacés par `purgeExpiredStories` après le rendu de la Communauté (`after()`), une story signalée et non traitée 7 jours de plus. Les progrès partagés restent des publications du fil. Les photos vont d'un bord à l'autre sur téléphone, « J'aime » et les commentaires sont posés dessus, un double-tap aime la publication ; `useBravo` (`reaction-store.ts`) garde le même « J'aime » dans le fil et sur les pages des publications. **Enregistrer** (icône sous chaque publication, `setPostSaved` dans `src/server/community/saves.ts`) : toute publication lisible, 500 au plus (`MAX_SAVED_POSTS`), privé (jamais montré à l'auteur), effacé avec le compte ou la publication (`post_saves`) ; un compte suspendu peut encore enregistrer. **Partager** (`ShareDialog`) : dans mon fil (`sharePost` : la publication d'un autre membre, citée sous mon mot par `posts.shared_post_id` ; partager un partage renvoie à l'origine, une seule fois par publication, le partage disparaît avec l'origine et compte dans la limite de publications), à une discussion ou un contact (message `kind: "post"`, voir Messagerie), « Copier le lien » et « Autres applis » (partage du téléphone). Le lien `/community/posts/[id]` est réservé aux membres connectés (`getFeedPost`, mêmes règles de visibilité et de blocage que le fil). Une publication citée (partage ou message) est relue pour la personne qui lit (`sharedPostsFor`) : masquée, retirée ou d'une personne bloquée, elle devient « n'est plus disponible ».
- **Photos et vidéos** : limites et schémas dans `src/features/community/media.ts` (4 photos ou 1 vidéo de 60 s / 50 Mo), stockage dans le compartiment **privé** « media » de Supabase Storage, utilisé uniquement par `src/server/storage/service.ts` (clé `SUPABASE_SECRET_KEY`, serveur seulement, facultative : sans elle, les boutons photo/vidéo sont masqués). **Seule exception** à « rien du navigateur vers Supabase » (approuvée par le fondateur) : le navigateur envoie un fichier directement au stockage avec une autorisation à usage unique créée par le serveur pour ce chemin (`requestUploads`) ; le serveur revérifie ensuite le fichier (présence, taille, type) avant de le joindre (`verifyMedia`). La lecture passe par des liens temporaires d'une heure. Les photos sont réduites et réencodées dans le navigateur (`media-client.ts`), ce qui retire la position GPS ; les vidéos ne sont pas encore réencodées (NEXT : Mux ou Cloudflare Stream). Supprimer une publication ou un compte supprime aussi ses fichiers. **Vues des vidéos** (2026-10-28) : une vue par personne et par publication après 2 secondes regardées (`recordVideoView`, `post_video_views`), jamais celle de l'auteur ; le nombre est public (pastille en haut à gauche de la vidéo, `FeedPost.videoViews`), qui a regardé ne l'est pas. Next garde les pages quittées cachées dans le DOM (Activity) : tout média qui joue (vidéo, audio) se met en pause dans le nettoyage d'un `useLayoutEffect`, sinon le son continue dans une autre catégorie (voir `PostVideo` : pause aussi hors de l'écran, une seule vidéo à la fois).
- **Messagerie** : règles et limites dans `src/features/messages/rules.ts` (fonctions pures testées : `sendPermission`, `layoutMessages`), logique dans `src/server/messages/service.ts`. Conversations privées entre membres du Centre, une seule par paire (`directKey`). Le premier message d'une personne inconnue arrive comme une **demande** : un seul message avant l'acceptation ; refuser la retire sans prévenir l'expéditeur. Chaque fonction revérifie la participation et les blocages (dans les deux sens). Pas de « Vu » ni de « En ligne » : `lastReadAt` ne sert qu'aux non-lus. Les messages ne sont jamais envoyés à Get iT AI ; un message signalé n'est visible par la modération que lui seul. Pas encore de temps réel : la conversation ouverte se rafraîchit toutes les 3 secondes, la boîte toutes les 10, la pastille toutes les 30 (`UnreadPoller`). **Pactes** (défi à deux) : règles pures dans `src/features/messages/pacts.ts` (`pactProgress`, `pactNeed`, `pactOutcome`), logique dans `src/server/messages/pacts.ts`. Un seul pacte ouvert par conversation (index unique partiel) ; chacun relie une habitude dont seul le « fait / pas fait » est partagé ; le pacte commence le lendemain de l'accord ; un jour manqué ne casse que la série commune ; la fin est réglée à l'ouverture de la conversation (`settlePacts`, pas de tâche planifiée) ; quitter montre seulement « Le pacte est terminé ». Les étapes (proposition, fin, arrêt) sont des messages `kind: "pact"` affichés selon l'état du pacte. Pas d'XP en plus : l'habitude en rapporte déjà. **Pactes de groupe** (discussion d'un groupe privé, `src/server/messages/group-pacts.ts`, `GroupPactPanel` en haut de la discussion ; règles pures `groupPactProgress`, `groupPactOutcome`) : proposé à tous les membres actifs (sauf personnes bloquées), chacun le rejoint en reliant sa propre habitude (ou en la créant) jusqu'au premier jour ; il commence le lendemain de la première acceptation, avec ceux qui ont accepté (2 au moins) ; réussi si **80 % des participants** ont fait assez de jours ; quitter retire seulement soi-même (sous 2 participants, le pacte se termine). `proposePactAction`, `respondPactAction` et `cancelPactAction` choisissent la version à deux ou de groupe selon la conversation. **Photos et vidéo** dans les messages : mêmes limites et envois vérifiés que les publications (`message_media`, `messages.media_count`, autorisation `requestMessageUploads` seulement là où la personne peut écrire) ; un message peut n'avoir que des photos (petit bouton d'options à la place de la bulle) ; liens lus par le cache d'`avatarUrls` (la conversation se rafraîchit toutes les 3 secondes) ; supprimer le message (ou le retirer en modération) supprime ses fichiers ; la modération voit les photos du message signalé. **Publication envoyée** : message `kind: "post"` (`messages.post_id`, mis à null si la publication est supprimée), envoyé depuis « Partager » d'une publication (`sendPostAction` : discussions récentes puis contacts, `listShareTargets` ; la discussion est créée au besoin et suit les règles de demande) ; la bulle montre un aperçu et « Voir la publication » mène à son lien.
- **Groupes** (`/groups`, bouton « Groupes » de la Communauté) : règles pures dans `src/features/groups/rules.ts` (limites alignées sur la migration, `canManage`, `canRemove`), logique dans `src/server/groups/service.ts`. Un groupe a un sujet (un pilier, ou général), un créateur (`owner`, il ne quitte pas : il supprime), des admins et des membres. **Public** = forum : tout membre du Centre le trouve dans l'annuaire (sujet, recherche), le lit et le rejoint ; ses publications sont des `posts` avec `group_id` (absentes du fil du Centre et des profils), et il faut en être membre pour publier, commenter ou dire bravo (`groupJoinRequired`) ; le créateur et les admins retirent une publication du forum. **Privé** = discussion de groupe dans la Messagerie (`conversations.group_id`, sans `direct_key`, `getGroupChat`, `GroupChatView`) : invisible pour qui n'est ni membre ni invité, sur **invitation acceptée** (refuser ne prévient personne), 20 personnes au plus ; les messages des personnes bloquées sont cachés, on n'invite pas une personne bloquée. Les fonctions des conversations à deux (`loadMembership`, pactes, demandes, contacts) ignorent les discussions de groupe. 10 groupes créés au plus par personne ; supprimer un groupe efface ses publications, sa discussion et leurs fichiers ; le groupe disparaît avec le compte de son créateur (NEXT : transfert au plus ancien admin). **Où les trouver** (2026-10-27) : les groupes privés sont dans la Messagerie, onglet « Groupes » (discussions, invitations à accepter, « Nouveau groupe privé » → `/groups/new?type=private`, retour vers la Messagerie) ; le bouton Groupes de la Communauté ne montre que les groupes publics. Dans un groupe **public**, tout membre invite (`canInvite`) et partage le lien (`ShareGroupButton` : copier, autres applis) ; dans un privé, seuls le créateur et les admins invitent. Les invitations à un groupe privé comptent dans la pastille de la Messagerie (`countPrivateInvitations`).
- **Contacts** (amis) : règles pures dans `src/features/contacts/rules.ts` (`contactState`, 50 demandes par 24 h), logique dans `src/server/contacts/service.ts`, une ligne par paire (`contacts.pair_key` = `directKey`). Page `/messages/contacts` (bouton « Contacts » en haut de la Messagerie) ; on ajoute aussi depuis le menu d'une publication ou d'une conversation. La liste reste privée (jamais montrée à quelqu'un d'autre). Un contact écrit directement, sans demande de message : devenir contacts accepte aussi la demande en attente (`acceptPair`). Refuser retire la demande sans prévenir ; bloquer supprime le contact (`blockUser`). Les demandes reçues comptent dans la pastille de la Messagerie.
- **Marketplace** : listes et limites dans `src/features/marketplace/rules.ts` (catégories, 17 régions du Québec plus « en ligne », tranches de prix, permis obligatoire des professions réglementées ; alignées sur les contraintes de la migration, un test le vérifie), logique dans `src/server/marketplace/service.ts`. Type de compte `Profile.accountType` : consommateur ou affilié, choisi à la première étape de l'onboarding, modifiable dans Réglages. Seul un affilié membre du Centre et non suspendu soumet une annonce ; elle reste `pending` jusqu'à la décision de l'équipe Get iT (rôle `admin`, `/marketplace/approvals`). Les acheteurs ne voient que les annonces `approved` d'un affilié non suspendu et non bloqué (`visibleWhere`) ; redevenir consommateur cache ses annonces sans les supprimer. Le nom, le courriel et le permis du vendeur ne servent qu'à l'équipe et ne sont jamais renvoyés aux acheteurs. Les photos réutilisent les envois des publications (`useMediaUploads({ photosOnly })`, même dossier `posts/<userId>`, supprimées avec le compte). Prix en cents, en CAD (`currencyDisplay: "narrowSymbol"`). Filtre « Où » des services (`mode`) : en ligne = région `online`, en présentiel = au moins une région du Québec (`IN_PERSON_REGIONS`) ; une annonce qui dessert les deux apparaît dans les deux. Pas encore de paiement ni d'avis : « Contacter le vendeur » ouvre la Messagerie. **Vitrine** (accueil des onglets Services et Gear, `src/features/marketplace/components/vitrine.tsx`) : recherche « Que veux-tu accomplir? » (paramètre `q`, titre et résumé), rangée de catégories en icônes (`VITRINE_CATEGORIES`, l'autre onglet au bout ; elle remplace les anciens onglets), puis des collections en grandes cartes : « Pour ton plan » (piliers des plans de Mon développement, sinon les piliers prioritaires) et « Nouveautés ». Une recherche, une catégorie, un filtre ou « Tout voir » (`view=list`) montre la liste filtrée (`isFiltered`). Pas de filtre par pilier (décision du fondateur, 2026-10-26 : les catégories en icônes le remplacent) ; le pilier d'une annonce sert aux collections « Pour ton plan », dont « Voir tout » garde `?pillar=` dans une pastille qui se retire (`CatalogFilterBar`). **Gear : bientôt** (décision du fondateur, 2026-10-26) : `GEAR_SALES_OPEN = false` ; l'onglet Gear affiche « Le Gear arrive bientôt », le formulaire « Vendre » ne propose plus que les services, et `createListing` refuse le gear (`gearSoon`) ; les annonces gear existantes restent en base, masquées. Pas de mise en avant par l'équipe pour l'instant (décision du fondateur) ; toute mise en avant payée devra être étiquetée. **Favoris** : le cœur d'une annonce (`FavoriteButton`, `setFavorite` : annonce visible revérifiée, 200 au plus) l'ajoute à « Mes favoris » (`/marketplace/favorites`, bouton du haut de la Marketplace) ; privé, jamais montré au vendeur, effacé avec le compte ou l'annonce (`listing_favorites`).
- **Objectifs et habitudes** : **3 objectifs en cours au plus par pilier** (`ACTIVE_GOALS_PER_PILLAR`, `hasActiveGoalRoom` dans `src/server/goals/service.ts`), revérifié partout où un objectif devient « en cours » : création, changement de pilier, « Reprendre », onboarding, propositions de Get iT AI et plans de Mon développement (erreur `goalLimit`). La **photo d'un objectif** (`Goal.photoPath`, `src/server/goals/photo.ts`, `GoalPhotoEditor` posé sur l'anneau de la fiche) remplace l'icône du pilier dans la fiche, la liste et « Ma journée » ; même chaîne que la photo de profil (`prepareAvatar`, dossier `posts/<userId>`, liens de `avatarUrls`), supprimée avec l'objectif. - **Niveaux et mode Ranked** (`/profile/ranked`, bouton « Passer en Ranked » à côté du niveau dans l'Aperçu) : tout le monde commence au niveau 1 de l'XP, et **sans Ranked les niveaux sont privés** (personne d'autre ne les voit : `getDisplayLevels` ne renvoie que les personnes classées, le fil, la Messagerie, les contacts et le profil public n'affichent rien d'autre ; le niveau ne se partage dans le Centre qu'en Ranked). L'âge, le sexe et le pays ne sont pas redemandés : ils viennent du compte (`getRankedPerson`) et sont gardés avec les réponses au moment de l'évaluation (`rankedRecordSchema`). Le Ranked ne classe que le **physique** et le **financier** (le social et le mental restent privés) : chaque pilier reçoit un niveau de 1 à 100, le pourcentage de la population du Canada et des États-Unis réunis que la personne dépasse, dans sa tranche d'âge (et son sexe pour le physique) ; le total est la moyenne des deux. Ces trois niveaux sont **obligatoirement publics** (case d'accord). Physique (`scoring.ts`, poids entre parenthèses) : course de 12 minutes convertie en VO2max puis registre FRIEND (25 %), pompes d'après les catégories de la SCPE, chacune supposée couvrir un cinquième de la population, les femmes sur les genoux (20 %), flexion assise d'après les percentiles du YMCA (15 %), IMC d'après la taille et le poids (10 %, décision du fondateur ; percentiles NHANES 2015-2018 par âge et sexe, courbe américaine aussi pour le Canada ; plus l'IMC est loin de la plage santé 18,5 à 24,9, plus le niveau baisse, tous à égalité dans la plage ; marqué « Estimation »), squats en 60 s d'après le test assis-debout d'une minute de la population chilienne (15 %, estimation) et saut sans élan d'après une estimation construite sur des moyennes d'adultes espagnols (15 %, estimation). Financier (un tiers chacun) : revenu net par heure travaillée (CPS ASEC, impôts retirés ; courbe américaine aussi pour le Canada), valeur nette = actifs − dettes (SCF et Enquête sur la sécurité financière, montants canadiens à parité de pouvoir d'achat), taux d'épargne (dépenses par rapport au revenu, SCF 2022, en partie estimé). Le calcul est déterministe et testé, **jamais fait par l'IA** ; tableaux sourcés dans `reference.ts` (chaque référence a `estimate`) et `reference-data.ts` (généré à partir des microdonnées ; à refaire lors d'une mise à jour des données). Questionnaire unique dans `questionnaire.ts` (taille, poids, morphologie en trois silhouettes ecto, méso, endo dessinées selon le sexe dans `body-type-picker.tsx` — la morphologie ne compte pas dans le niveau, elle sert d'indication à Get iT AI —, puis les tests et les finances ; consignes de chaque question dans `Ranked.questions`) ; avis de décision automatisée (Loi 25, art. 12.1). Une évaluation au plus tous les 30 jours (`ranked_evaluations`, la plus récente fait foi, le niveau peut descendre) ; quitter le mode Ranked efface tout. L'XP continue de compter (séries, récompenses) ; dans l'orbite de l'Aperçu, physique et financier montrent le niveau classé, mental et social la progression d'XP. Get iT AI peut analyser le niveau (une fois par évaluation, `ranked_analysis`, finances envoyées en percentiles seulement). **Classement** (`/profile/ranked/leaderboard`, `getLeaderboard`, règle pure `rankEntries` : même niveau = même rang) : les personnes en Ranked et membres du Centre, par niveau total, physique ou financier, tout le monde ou « Mes contacts » (100 premiers et ma place), sans les personnes bloquées ; accessible depuis la page Ranked et l'Aperçu du Profil.
